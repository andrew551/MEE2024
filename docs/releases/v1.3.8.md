# MEE2024 v1.3.8

Windows executable, no Python installation required. Double-click for the app window, or run
it from a terminal for the command line; the classic interface is still there with
`MEE_2024_v1.3.8.exe gui`.

**This is the first release since v1.3.5.** v1.3.6 and v1.3.7 were built and tested in the
field but never published, so everything they carried is here. If you are coming from v1.3.5,
four things are worth knowing before anything else:

- **Your batch output no longer overwrites itself.** In v1.3.5 a second run pointed at the
  same output folder silently destroys the first run's summary and log.
- **Successful command-line runs no longer exit with code 1.** In v1.3.5 every scripted run
  reports failure to the shell, whatever it actually did.
- **There is a calibration library.** Build masters once, and each field is matched to the one
  that fits its own frames.
- **SER files are read directly**, with no conversion and no second copy of a 15 GB file.

---

## Fixed: batch output overwriting itself

`batch_summary.csv`, `batch_summary.json` and `activity.jsonl` have fixed names and used to be
written straight into the output folder you chose, so a second run pointed at the same folder
silently destroyed the first run's summary and log. The per-field archives survived, being
timestamped; the account of what happened did not — and that account is what found the two
failed fields in a set of eighteen.

Each run now writes into a subfolder named for its input — `.../Zenith`, with the field tree
inside — and a timestamp is appended only when a previous run's records are already sitting
there.

## Fixed: the records a run writes were unreachable

The run folder, the batch summary and the per-field logs were all being written to disk and
nothing in the app window opened any of them. The single "Open output folder" button pointed
at whichever field ran *last* — so it opened one arbitrary field rather than the run root —
and it appeared only on success, which is backwards: a failed run is when you want the log.

It now points at the run root, appears whether the run succeeded, failed or was cancelled, and
every row of the batch table opens that field's own folder.

**Every field folder now explains itself.** Each one carries a `field_summary.json` and its own
slice of the activity log, so a folder copied to another drive or handed to whoever is
reducing says what produced it without the folder above it. Failed fields get one too — the
absence of a folder is not a diagnosis.

## Fixed: successful command-line runs exited with code 1

`mee2024 stack` and `mee2024 distortion` always exited with code 1, even when they succeeded.
They return the archive they wrote — useful when calling them from Python, and wrong as an
exit status, because `sys.exit()` treats any non-integer as an error message. So
`mee2024 stack ... && next-step` never ran the next step, and any script checking the exit
code saw every successful run as a failure. It has been there a long time and affects exactly
the scripted, unattended path the command line exists for.

## New: the calibration library

There was no way to build a master dark or flat except as a side effect of a light run, which
left it keyed to nothing and impossible to find again.

```bash
mee2024 calibrate --library LIB --darks "...\DARKS" --flats "...\FLATS"
```

or the **Build library** button in the app window. Then point a folder run at the library and
**each field gets the master that matches its own frames**, announced in that field's log and
recorded in its summary.

- **Keyed on camera, gain, exposure and binning.** Nothing else.
- **Temperature is recorded and warned about, never keyed.** For a cooled body the setpoint is
  what makes a dark comparable; for an uncooled one the temperature is measured rather than
  chosen, so keying on it would mean never matching. Segregate by temperature yourself and the
  library will tell you when the frames disagree with the master.
- **Nothing is scaled or interpolated.** A defect is `pedestal + rate × time` — the pedestal is
  63% of a defect at 0.1 s and 1.7% at 10 s — so a tier borrowed from its neighbour is wrong
  rather than approximate. A missing tier is reported as missing, with the tiers that do exist
  listed, and the field runs uncalibrated rather than mis-calibrated.
- **No flat-darks needed**, and the reason is checked rather than assumed: what makes it valid
  is the flat's mid-range fill, so the builder measures the fill and says so when it is outside
  25–75% of full scale.
- **One flat set serves every gain**, on the stated assumption that PRNU and vignetting are
  gain-independent to first order. The library says so each time it does it.
- **Frame types are read from `OBJECT`, never `IMAGETYP`** — which reads `'Light'` on every
  scripted dark, because the capture sequencer cannot set it. Folders of darks and flats under
  a batch root are now recognised and left out instead of being stacked, plate-solved and
  failed.

Built and validated on the León eclipse campaign data: **9 masters from 449 frames of 26
megapixels in 324 seconds**, then two fields reduced end to end with the right tier matched
automatically. `docs/LEON_2026-08-11.md` has the measurements.

**It also removed a memory ceiling from ordinary runs.** Combining darks used to hold every
frame in memory at once — 5.2 GB for fifty frames of a 26 MP ASI2600MM, and 10.4 GB while the
list and the array both existed, which is more than most machines have. It streams now, so a
full dark tier can be combined at all.

## New: SER files can be read directly

A 61-megapixel camera at 3.2 fps is **122 MB per frame and 388 MB/s sustained**. Capture
software cannot write FITS-per-frame at that rate, so the frames go into a SER container —
and until now the only way in was a conversion through PIPP, costing a duplicate of a 15 GB
file and, it turns out, **destroying the timestamps** on the way through.

```bash
mee2024 stack "capture.ser"
```

A `.ser` file is a *container*: it expands into one frame each, addressed as
`capture.ser#42`. Everything downstream — stacking, alignment, the batch table, the
calibration library, the logs — works on them exactly as on FITS files. Reading a frame is a
seek, so a 22 GB capture costs one frame of memory rather than 22 GB.

The `.CameraSettings.txt` file your capture software writes alongside supplies what a FITS
header would: exposure, gain, offset, binning, camera, serial number, both temperatures, and
UTC start/middle/end. `MidCapture` is actually **better than FITS `DATE-OBS`** — it is the
mid-exposure epoch. It also carries something FITS has no equivalent for: confirmation that
no dark, flat, background subtraction or banding suppression was applied.

**Worth knowing about your captures:** a SER file can carry a UTC stamp *per frame*, which
is better than FITS gives you (one `DATE-OBS` per file). Of three real captures examined, two
had them and one did not — and the one that did not is the one that ended abnormally, on eight
blank frames. The trailer is written when a capture completes, so a capture that dies takes
its per-frame timing with it. Nothing recovers it afterwards.

## New: choosing which frames to use, without making a copy

A capture rarely starts and stops on the science. The trim used to be a manual pass through a
separate program that wrote a second copy of the file. It is now a run parameter:

```bash
mee2024 stack "capture.ser" --frames 50-172
```

Zero extra storage, nothing rewritten, the container's metadata preserved by construction,
and the trim recorded in the results so it is reproducible rather than an untracked manual
step. Changing your mind is free.

**Every run also measures its frames and suggests a range** — a strip through each, about a
second for 180 frames of a 22 GB container:

```
frames 50-171 of 180 look usable; 50 dropped at the start, 8 at the end;
(8 blank, 39 saturated above the 4.6% floor, 11 still changing).
Set frame_range to 50-171 to use only those; nothing has been dropped automatically.
```

Nothing is dropped without being asked. Both ends are treated identically, because **the Sun
can be at the end of the last file as well as the start of the first**. It works on a folder
of FITS as well as on a container.

Measured against real manual trims: within one frame of the human answer on a 180-frame
eclipse capture, and correct on two separate sequences that run *into* the returning Sun.

## New: a frame that lies about its exposure is now reported

Capture software that changes exposure mid-sequence can write the **new** exposure into the
header of a frame that still holds the **previous** exposure's pixels — the camera had not
applied the change when the frame was read out. Nothing downstream can detect this: the file
is well-formed, the header is self-consistent, and the frame simply carries half the signal
it claims. It would then be stacked into the wrong exposure tier and matched to the wrong
master dark.

Six frames of one real eclipse ladder are exactly this. Every run now says so:

```
SCI_ladder_00006.fits says EXPTIME 1.2 s, but it is the first frame after a change from
0.6 s and its level (2750) looks like the 0.6 s frame before it (2768) rather than like
the other 1.2 s frames (4620).
```

**It reports rather than corrects.** Eclipse data is too scarce to drop frames over a label,
and an automatic relabel would be a silent edit of your data. It also serves a second
purpose: a run on data nobody has checked by hand says so in the log, before anyone trusts
the output.

Turn either off with `--no-scan` and `--no-exposure-check`, or the `scan_frames` and
`check_exposures` settings.

## Also new

- **Pick several folders in batch mode.** Ctrl-click in the folder dialog, or select rows in
  the in-page picker. Reducing two fields out of eighteen after a rerun no longer means two
  runs.
- **A stray file in a session root no longer swallows the tree.** A folder holding a single
  photograph beside the real capture tree used to be claimed as the one and only field, and
  everything beneath it skipped. A folder outnumbered ten to one by what lies below it is now
  treated as a container; a capture folder with a small `thumbnails` subfolder is still a field.
- **Darks and flats picked in single mode no longer leak into folder runs.** They stayed
  selected and were applied to every field, invisibly, with no way to see or clear them.
- **The observation epoch is decided where the data is.** Correctness used to depend on which
  of the three interfaces you used, and the command line — the one most likely to be scripted
  and left running — still fell back to a 2023 default. `--date`, `--date-from-header` and
  `--guess-date` join the CLI, and a date you give that disagrees with the frames is reported.
- **The 2-D residuals are saved as `TWOD_RESIDUALS.csv`**, not only drawn into a 600 dpi PNG:
  position, dx/dy in pixels and arcseconds, radius, magnitude and catalogue ID.
- **Master darks and flats carry provenance** — exposure, gain, offset, both temperatures,
  camera, optical train and the folder they came from. A master that cannot identify itself
  cannot be safely reused, which is the only reason to save one.

## Also fixed

- **A capture path with an unusual character could kill a run mid-flight.** The log file was
  opened in the platform's default encoding, and it writes the frame list verbatim, so one
  character Windows' cp1252 cannot hold raised an error from the logging call rather than from
  anything to do with the data.
- **Taking more darks silently masked more pixels.** The defect threshold was a multiple of the
  master's own noise, which falls as 1/√N — so 20σ was 5.3 ADU with 50 darks and 8.7 ADU with
  10, and a longer calibration run changed which stars reached the fit. There is now a floor of
  10 ADU above bias, which is what actually moves a centroid (~37 mas at 2 px from a 1000 ADU
  star). It can only mask fewer pixels than before, never more.
- **A pedestal warning that fired on every correctly calibrated frame.** It triggered whenever
  any single pixel was below zero, which on 26 million pixels is always true. The pedestal is
  still always recorded; the warning now waits until more than 1% of the frame is negative,
  which is what a genuinely mismatched dark looks like.
- Pattern databases are released before a rebuild, so one cannot fail with a permission error
  on a file the same session had mapped.
- The classic interface's file dialogs no longer open on whatever directory Windows launched
  the executable from.
- A leaked log handle in the catalogue reader (found by Douglas), and a "pixels were clipped"
  warning that could never fire and would have been wrong if it had — the values are kept in a
  wider type, not clipped.

## Notes for anyone reading the code

Three measurements that contradict what the format documentation would lead you to write, all
recorded in `docs/SER_INPUT.md`:

- The SER **`LittleEndian` header field is wrong** on every file examined — it reads 0
  (big-endian) while the pixels are little-endian. The byte order is measured from the pixels
  instead, by counting distinct byte values. Two more obvious tests were tried first and both
  fail; the doc says why, because both look right.
- A timestamp trailer of the correct **size** can be entirely zeros — the space is allocated
  whether or not timestamping was on.
- SER header strings are **not zero-filled**: they carry leftover memory after the
  terminator.

## Measured, and not yet acted on

From the León eclipse campaign, recorded in `docs/LEON_2026-08-11.md`:

- **The eclipse was 9.7° above the horizon**, and at that altitude the curvature of vertical
  refraction across the field — the part neither the plate solve nor the fit's linear terms can
  absorb — is **0.50″**, about 4× the 111–116 mas these fields actually fit at. At the bottom
  of the refraction mosaic (5.0°) it is 2.28″, a full pixel. Refraction correction is still off
  by default and still unreachable from the app window.
- **FITS site coordinates cannot be trusted.** In this set they are 17.8 km wrong, pointing at
  the nearest city rather than the site, and there is no altitude keyword at all — the same
  trap as the Bruns 2017 eclipse data. Check yours against your own site record.
- **Read noise measures 25–30% below the header's `RDNOISE`** at both gains, consistently.
  Worth resolving before that number is used in an error budget.
- The site ran at **895–898 hPa** against a pipeline default of 1010, and 21–24 °C on the
  observing nights against a default of 10. Together with the unmodelled 1101 m of elevation,
  the defaults overstate refraction by 15.7%.
- The plate scale predicted from `FOCALLEN` and `XPIXSZ` agrees with the fitted value to
  **0.45%**, which makes it a usable prior for the solver.
